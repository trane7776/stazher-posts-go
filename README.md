# stazher-posts-go

сервис постов и вложенных комментариев на go с graphql.

## запуск

из папки проекта:

```sh
docker compose up -d db
docker compose exec -T db psql -U posts -d posts -v ON_ERROR_STOP=1 < migrations/001_create_posts.sql
docker compose exec -T db psql -U posts -d posts -v ON_ERROR_STOP=1 < migrations/002_create_comments.sql
docker compose exec -T db psql -U posts -d posts -v ON_ERROR_STOP=1 < migrations/003_comments_parent_index.sql
docker compose exec -T db psql -U posts -d posts -v ON_ERROR_STOP=1 < migrations/004_comments_replies_count.sql
docker compose up --build -d app
```

развертывание бд и приложения, запуск миграций в бд.


## запросы

адрес: http://localhost:18080/query

отправлять post-запрос с заголовком `content-type: application/json` и json-телом.
для создания поста и изменения настройки комментариев добавлять `x-user-id: tim`. это тестовая идентификация пользователя.

список постов:

```json
{
  "query": "{ posts(limit: 10, offset: 0) { id title authorID commentsEnabled } }"
}
```

пост и страница корневых комментариев:

```json
{
  "query": "{ post(id: \"1\") { id title body } comments(postID: \"1\", rootsOnly: true, limit: 10) { id parentID body repliesCount } }"
}
```

ответы на конкретный комментарий:

```json
{
  "query": "{ comments(postID: \"1\", parentID: \"10\", limit: 10) { id parentID body repliesCount } }"
}
```

`parentID` заменить на id выбранного комментария. возвращаются только непосредственные ответы; для следующего уровня передать id ответа. сначала загружать корни, затем раскрывать ветки — родитель уже будет на странице.

`repliesCount` — число непосредственных ответов, без всех дальнейших потомков. по нему на сайте можно показать кнопку «показать ответы (5)». количество не зависит от размера загруженной страницы.

в postgresql счётчик хранится в `replies_count`. создание ответа и увеличение счётчика его родителя выполняются в одной транзакции. миграция заполняет счётчики для существующих комментариев.

вложенное поле `replies` не использовал, чтобы избежать n+1 при отдельной загрузке ответов для каждого комментария. api рассчитан на постепенное раскрытие дерева: сначала корни, затем ответы выбранной ветки.

для следующей страницы передать `after` с id последнего элемента этой же выборки. у корней и каждой ветки свой курсор. без `rootsOnly` и `parentID` возвращается общая страница комментариев поста, как раньше. одновременно `rootsOnly: true` и `parentID` передавать нельзя.

## мутации

создать пост:

```json
{
  "query": "mutation { createPost(title: \"первый пост\", body: \"текст поста\") { id title authorID } }"
}
```

добавить комментарий:

```json
{
  "query": "mutation { createComment(postID: \"1\", body: \"комментарий\") { id postID body } }"
}
```

для ответа добавить аргумент `parentID` с id родительского комментария. текст — до 2000 символов.

отключить комментарии от имени автора поста:

```json
{
  "query": "mutation { setCommentsEnabled(postID: \"1\", enabled: false) { id commentsEnabled } }"
}
```

чтобы включить обратно, передать `enabled: true`.

## хранилища

- `memory`: данные в map, отдельные списки id для порядка и пагинации, доступ защищён через `sync.RWMutex`. при перезапуске данные теряются.

- `postgres`: таблицы `posts` и `comments`, родитель комментария хранится в `parent_id`. добавление комментария проверяет настройку поста в транзакции с блокировкой строки. пагинация комментариев — по id, без offset.

оба варианта реализуют интерфейс `Store`. compose запускает сервер с postgresql.

запускать локально с памятью:

```sh
go run ./cmd/server -storage=memory
```

локально с postgresql, когда база из compose уже работает:

```sh
export DATABASE_URL='postgres://posts:posts@localhost:5432/posts?sslmode=disable'
go run ./cmd/server -storage=postgres
```

## тесты

unit-тесты в `internal/store/store_test.go` проверяют хранилище в памяти:

- создание поста, корневого комментария и ответа с правильным родителем;
- пагинацию постов и комментариев, выборку корней и непосредственных ответов, их количество;
- длину комментария: 2000 символов допустимо, 2001 и пустая строка — ошибка;
- отключение и включение комментариев автором, запрет записи и отказ чужому пользователю;
- ошибки для несуществующего поста, отсутствующего родителя и родителя из другого поста;
- параллельную запись комментариев из 100 горутин и чтение из ещё 100: сохранность записей и уникальность id.

```sh
go test ./internal/store
CGO_ENABLED=1 go test -race ./internal/store
```

## производительность

- в памяти поиск идёт через map, для постов и веток есть отдельные списки id с бинарным поиском. в postgresql есть индексы `(post_id, id)` и `(post_id, parent_id, id)`.

Для решения проблемы n+1 запросов и глубокой вложенности было принято архитектурное решение - ленивая загрузка ответов: сохранять количество ответов в бд, и если нужно делать загрузку ответов, т.е.

Интерфейс сначала показывает корни, затем по нажатию показать ответы(например 3) загружает детей. Глубина поддерживается повторением этой операции на любом уровне.

Pub/sub не реализован
